

假设一个 Java 客户端向服务器发送 HTTPS 请求。

首先，如果没有可复用的连接，客户端需要通过 DNS 解析获得服务器 IP，然后通过 TCP 三次握手建立连接，接着进行 TLS 握手，完成身份验证和密钥协商。

之后客户端构造 HTTP 请求。数据进入网络协议栈，经过 TLS 加密，TCP 层添加源端口、目标端口、序列号等信息；IP 层添加源 IP、目的 IP；链路层封装成帧，通过网卡发送出去。
数据在网络中经过路由器转发，路由器主要根据目标 IP 查找路由表，确定下一跳，每一跳都会使用对应的链路层地址。
到达服务器后，网络协议栈逐层处理数据。TCP 负责可靠、有序地交付字节，TLS 完成解密，HTTP 服务器解析请求并交给业务程序。
服务器处理完成后，构造 HTTP 响应，按照类似过程传回客户端。
通信完成后，TCP 连接可以继续复用，也可以通过四次挥手正常关闭。

### 三次握手


Seq序列号 ： 数据排序、定位
接收方可以去除重复的数据；
接收方可以根据数据包的序列号按序接收；
可以标识发送出去的数据包中， 哪些是已经被对方收到的（通过 ACK 报文中的序列号知道）

Ack确认号：确认已连续收到的数据

1.三次握手才可以阻止重复历史连接的初始化（主要原因）
导致服务端建立了一个历史连接，又白白发送了数据，妥妥地浪费了服务端的资源。


2.三次握手才可以同步双方的初始序列号

3.三次握手才可以避免资源浪费
由于没有第三次握手，服务端不清楚客户端是否收到了自己回复的 ACK 报文，所以服务端**每收到一个 SYN 就只能先主动建立一个连接**

### 粘包 拆包

**TCP 是字节流协议，不保留应用层的消息边界，**`read()` **的读取边界与业务消息边界没有必然联系。**

**解决方案：**
1.固定长度：每条消息占固定字节数。
2 分隔符：使用特殊字符标识消息结束，注意转义问题。
3.长度字段：先读取固定长度的消息头，获取消息体长度，再读取完整消息体。
